    // Two records, one release

    What your team knows. What your customers read.

    Every change carries an internal description for the team and, optionally, a public one. Only changes with a public description can ever reach the public page, and only after approval.

    1. 01ProjectA product, its team, branding and public page
    2. 02ReleaseA version with type, channel and release date
    3. 03ChangesFeature, fix, security, performance and more
    4. 04RevisionA frozen copy of the public notes for approval
    5. 05SnapshotThe published page. It can't be edited, only revoked

    // Publishing

    Nothing goes public on one person's say-so.

    The author freezes the public notes into a revision. Someone else approves exactly that revision, and an Admin or Release manager publishes it. Change a word afterwards and it needs a new revision.

    1. Draft
    2. Internal review
    3. Approval revision
    4. Approved
    5. Published
    Step

    Draft

    Write the release and its changes. Internal notes stay internal.

    Done by Developer Admin, Release manager or Developer

    Self-approval is refused by the server, even for system administrators, and every decision is in the audit log.

    // GitHub import

    Bring your release history with you.

    The importer reads a repository's GitHub releases and publishes them through the same approval flow. Four-part hotfix tags become proper versions, and pull-request titles are tidied into readable public notes.

    GitHub tagDocPulse versionType
    stable-3.1.03.1.0Minor
    stable-3.2.03.2.0Minor
    stable-3.2.0.13.2.0-hotfix.1Hotfix
    stable-3.2.43.2.4Patch
    One pull-request line

    * feat/k4x9q2 dark mode for reports by @octo-dev in https://github.com/acme/web/pull/128

    ↓

    FeatureDark mode for reports

    The author handle and link stay in the internal notes. The real GitHub release date is kept, and re-running the import skips what's already there. The importer script is in the source repository.

    // Security

    Public pages read approved snapshots only.

    The public site can't see drafts or internal notes. Published snapshots can't be edited, only revoked.

    • Two-person approval
    • Immutable snapshots
    • Single sign-on (OIDC)
    • HttpOnly sessions
    • Rate-limited public API
    • Content Security Policy

    // Setup

    Running on your own server in five minutes.

    DocPulse ships as four Docker images. One compose file starts them with PostgreSQL and Redis, and serves the release pages and the admin portal from a single port.

    1. 01 · Before you start

      Any Linux, macOS or Windows machine with Docker and Docker Compose v2 (included in current Docker Desktop and Docker Engine), and about 2 GB of free memory.

    2. 02 · Download the two files 
      mkdir docpulse && cd docpulse
curl -fsSLO https://qulaxy.com/DocPulse-Site/setup/docker-compose.yml
curl -fsSL -o .env https://qulaxy.com/DocPulse-Site/setup/env.example
      mkdir docpulse; cd docpulse
Invoke-WebRequest https://qulaxy.com/DocPulse-Site/setup/docker-compose.yml -OutFile docker-compose.yml
Invoke-WebRequest https://qulaxy.com/DocPulse-Site/setup/env.example -OutFile .env
    3. 03 · Set the secrets

      Open .env and give POSTGRES_PASSWORD and the six secrets long random values. This fills them all in for you:

      for k in POSTGRES_PASSWORD JWT_ACCESS_SECRET BOOTSTRAP_SECRET WORKER_SECRET \
         NOTIFICATION_SECRET GITHUB_WEBHOOK_SECRET DEPLOYMENT_WEBHOOK_SECRET; do
  sed -i.bak "s|^$k=.*|$k=$(openssl rand -hex 32)|" .env
done
      $rng = [Security.Cryptography.RandomNumberGenerator]::Create()
$env_ = Get-Content .env
foreach ($k in 'POSTGRES_PASSWORD','JWT_ACCESS_SECRET','BOOTSTRAP_SECRET','WORKER_SECRET',
               'NOTIFICATION_SECRET','GITHUB_WEBHOOK_SECRET','DEPLOYMENT_WEBHOOK_SECRET') {
  $b = New-Object byte[] 32; $rng.GetBytes($b)
  $env_ = $env_ -replace "^$k=.*", ("$k=" + (($b | ForEach-Object { $_.ToString('x2') }) -join ''))
}
$env_ | Set-Content .env
    4. 04 · Start it 
      docker compose up -d

      Open the admin portal at http://admin.localhost:8080, choose Create its first admin and enter the BOOTSTRAP_SECRET from .env. Release pages appear on http://localhost:8080. The first start takes a minute while the database is prepared.

    // Your own domain

    Point two names at the server, such as releases.example.com and admin.releases.example.com, and set PUBLIC_URL and ADMIN_URL in .env. Put HTTPS in front with your usual proxy, and list it in TRUSTED_PROXY_IPS.

    // Updates

    docker compose pull
docker compose up -d

    Database changes apply automatically on start. Pin a version with DOCPULSE_VERSION in .env.

    // Backups

    docker compose exec postgres \
  pg_dump -U docpulse docpulse > backup.sql

    Email delivery and malware scanning for attachments are optional and set in .env.
